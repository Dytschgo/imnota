# Export failures

Status: living reference. Sections 1–4 describe current behaviour as of this change; sections 5 and 6 mark which work is done and which is proposed. A proposed item is not authorization to implement it.

## Purpose and scope

This page lists how prompt-bundle export ("Copy Bundle": plan → render → write → finish → copy) can fail, what the user sees, and how failures are reduced and tested. It covers the renderer export controller, the main-process bundle store and workflow, and the native clipboard writers. Hosted sharing is out of scope. For the overall export design see [Architecture — Prompt export](architecture.md#prompt-export); for receiver behaviour after a successful copy see the [clipboard receiver matrix](clipboard-receiver-matrix.md) and [clipboard compatibility plan](clipboard-images-plan.md).

## How errors travel

1. **Main process.** IPC workflow handlers registered through `handleWorkflow` (`electron/ipc-router.ts`) run inside `workflowOutcome` (`electron/workflow-errors.ts`). A thrown `NativeWorkflowError` keeps its code, message, `retryable` flag and `details`. A `ZodError` becomes `invalid-input`. Node filesystem errors preserve `details.errno`, with `ENAMETOOLONG` mapped to `path-too-long` and other errno values to `io-failure`. Remaining errors are classified by keyword matching on their message (`inferredCode`) and default to `io-failure`.
2. **Bridge.** The result crosses IPC as a `WorkflowResult` whose failure is a `WorkflowError` (`src/shared/workflow-bridge.ts`, built by `workflowFailure` in `src/shared/workflow-errors.ts`).
3. **Renderer.** `unwrap` and `nativeFailure` (`src/renderer/export/prompt-export-controller-helpers.ts`) turn a `WorkflowError` into a `ControllerFailure` with a `PromptBundleControllerErrorCode`. Renderer-side errors are created with `failure(...)`; anything else passes through `publicError`.
4. **Display.** `PromptSharingDialog` shows the error banner with optional technical details and an optional recovery button (Retry cleanup, Try again or Rebuild bundles); failures requiring a different action have no recovery button. `PromptBundleCard` shows a per-card error unless the dialog already reported it, and shows clipboard delivery warnings from `describeCopyDelivery` (`src/renderer/export/clipboard-delivery.ts`).

Introduced by this change:

- A renderer failure catalog, `src/renderer/export/export-failure-catalog.ts`, maps each classified failure to its user message and recovery action.
- Selection failures carry the existing card action identity (plan, artifact session and bundle number). The dialog places fallback actions under that current card and directs Rebuild bundles to it, including Markdown-only failures before files exist. If the identity no longer matches after replanning, or a plan-level failure has no selection, recovery uses the first errored card or the first current card; with no cards, Rebuild uses the plan-level action.
- Try again uses the retry action associated with the exact error currently displayed. Superseded or cancelled completions, successful previews, and actions rejected as busy or disposed cannot replace an outstanding failure's retry. Export retries use the same bundle number's current card and preserve the clipboard variant; if that bundle disappeared, retry rebuilds for a new choice without copying. A failed preview retries the preview read or composition without writing to the clipboard; a successful preview clears only its own earlier failure. When no retry target matches the displayed error, the dialog omits Try again and `retry()` does nothing.
- Direct Copy Markdown only before files exist uses `copyPromptExportMarkdown` through `workflow:prompt-export:copy-markdown`. Its argument contract is in `electron/ipc-contracts.ts`; `assertClipboardText` enforces the size limit before the existing clipboard writer runs. `workflowOutcome` preserves clipboard failure reasons for catalog messages and recovery. Legacy `system:copy-text` and its non-export callers retain their existing contract. This changes error transport, not clipboard transactions or export file writes.
- Main-process export and clipboard paths throw explicit codes instead of relying on keyword inference. Clipboard failures carry `details.reason` (`too-large`, `busy`, `prior-content`, `rejected`, `decode`); filesystem failures carry `details.errno`. In `electron/workflow-errors.ts` these are built by `clipboardFailure` and `filesystemFailure`; errors with a Node error code are treated as filesystem failures before keyword inference is tried.

## Failure catalog

Messages are paraphrased; the source is authoritative. "Where" names the file and function or class that raises the failure.

### Saved context and staleness

| Failure                                                  | Typical trigger                                                                 | Where                                                                                 | Recovery                                             |
| -------------------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| Unsaved drawing or text                                  | Content editor flush fails before planning                                      | `src/renderer/App.tsx` `getSavedPromptContext`                                        | Save the drawing or text, export again               |
| Pending external workspace change                        | Another process changed the project; reload not yet reviewed                    | `src/renderer/app/useProjectPersistence.ts` `getSavedContext`                         | Reload and review, export again                      |
| Screenshot or project-details flush failed               | Save of screenshot edits or project metadata fails                              | `useProjectPersistence.ts` `getSavedContext`                                          | Fix the save problem, export again                   |
| Workspace changed during flush                           | External change arrives while edits are being saved                             | `useProjectPersistence.ts` `getSavedContext`                                          | Reload and review, export again                      |
| Other saved-context error                                | Any message outside `SAVED_CONTEXT_GUIDANCE`                                    | `src/renderer/export/prompt-export-controller-core.ts` `readSavedContext`             | Generic "Latest changes could not be saved" guidance |
| Collection missing                                       | Collection deleted between save and snapshot                                    | `src/renderer/export/prompt-export-snapshot.ts` `capturePromptExportSnapshot`         | Reload the project, export again                     |
| Drawing PNG unavailable                                  | Drawing item has no saved image                                                 | `prompt-export-snapshot.ts` `capturePromptExportSnapshot`                             | Save the drawing, export again                       |
| Picture, text or drawing changed after planning          | Edit or external change between planning and render                             | `src/renderer/export/prompt-export-pipeline.ts` `PromptExportPipeline`                | Save, export again                                   |
| Stale card, older session, another project or collection | Action on a card from an earlier plan, or after switching project or collection | `prompt-export-controller-core.ts` `assertArtifactContext`, `validateArtifactContext` | Use the latest card or prepare fresh files           |

| Failure                                                      | Typical trigger                                                                                                                                                                          | Where                                                                                                 | Recovery                                                                                  |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |

## Known message problems before this change

Kept as context for the catalog work:

- Classified renderer errors (decode, canvas, encode, composition mismatch) reached `publicError` as plain `Error`s and were shown as "Prompt export failed unexpectedly. Try Rebuild bundles."
- Native codes were inferred from message keywords. "Context is too large to copy" contains neither "clipboard" nor "too long", so it became `io-failure` and was shown as a disk or folder-access problem. A busy Windows clipboard ("The clipboard is in use by another app") was coded `clipboard-limit`.
- Codes without a mapped message in `nativeFailure` showed raw OS or library text.
- The dialog offered Rebuild bundles for every error with a card, including errors a rebuild cannot fix, and offered no action when there were no cards.
- The same error could appear in the dialog banner and on the card.

This change addresses these through the failure catalog and explicit native codes.

## Plan to reduce failures

| Priority | Work                                                                                                                                                                                                                                                        | Status                                                            |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| P1       | Accurate messages and recovery actions: failure catalog, explicit native codes and details, one display location, actions that match the failure.                                                                                                           | In progress (this change)                                         |
| P2       | Automatic recovery: one silent re-plan on staleness; retry the final staging rename with the `atomicWrite` backoff; one retry after a busy Windows clipboard; reset the cached handoff root failure.                                                        | Proposed; consequential, needs independent review per `AGENTS.md` |
| P3       | Prevention: preflight that names the oversized picture; disable unavailable fallbacks on file-only bundles; allow links that resolve inside the workspace (needs security review); consented "replace clipboard" when existing content cannot be backed up. | Proposed                                                          |
| P4       | Cleanup hygiene: report or remove stale staging and recovery folders; prune temporary handoff folders during long-running sessions (pruning currently runs only when the handoff root is first prepared).                                                   | Proposed                                                          |

The real-engine retry regressions in `prompt-export-controller-core.test.ts` hold a Rich copy pending across cancellation and a newer Copy image failure, fail a preview read with `EBUSY` after a successful copy, and preserve a failed copy's retry across successful previews. Direct Markdown-only tests cover `too-large` and `rejected` catalog messages with `use-files` recovery before any export session starts. `electron/ipc-boundary.test.ts` covers the new channel's preload/handler consistency, sender restrictions, argument validation, size refusal before clipboard access, and structured native failures.

## Maintenance

When adding or changing an export failure, add or update its catalog entry and a test that reaches it, then update this page. Keep file and function references current; prefer names over line numbers.
